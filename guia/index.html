Guía white label

Una sola base de código para muchas apps de citas. Cada negocio tiene su propia app en la tienda, su web, su Firebase y su marca, y todo se controla desde un archivo de configuración.

👩‍💼 Soy administradorUso la consola web. No necesito programar ni abrir una terminal. 👨‍💻 Soy devUso los comandos npm run tenant, reviso el código y arreglo lo que falle.
Las dos formas hacen lo mismo. Lo que guardas en la consola se sube al repo, y lo que haces con comandos se ve en la consola. Cada receta de esta guía trae las dos versiones.

Conceptos clave

PalabraQué es
Negocio (tenant)Cada cliente que renta la app. Vive en la carpeta tenants/<id>/. El id va en minúsculas y con guiones, por ejemplo nails-ana.
tenant.jsonEl archivo de configuración del negocio: nombre, paquete, colores, rubro, módulos, Firebase, integraciones y datos iniciales. Nunca lleva contraseñas.
ProtegidoUn negocio ya publicado, como PeachGlow. No se puede eliminar, y lo que rompería su app instalada está bloqueado 🔒.
Plantillatenants/plantilla/: un negocio de ejemplo que nunca se despliega. Sirve de base y de prueba en el CI.
RubroPestañas, uñas, barbería, spa, estética o genérico. Pone las palabras de la app ("clienta" o "cliente", "lashista" o "barbero"), las categorías y la ficha de salud.
MódulosLo que incluye el plan del negocio (pagos, lealtad, anuncios, propinas…). Un módulo fuera del plan desaparece de la app. Uno incluido se prende y apaga desde la app del negocio.
SecretoContraseñas y llaves: token de Mercado Pago, cuentas de servicio, keystore. Se guardan cifradas en GitHub o en Firebase, nunca en el repo.
EnvironmentEl "cajón de secretos" de cada negocio en GitHub (Settings → Environments → <id>).
.aabEl archivo que se sube a Google Play. Hace falta uno nuevo solo si cambia algo marcado con 🔶 .aab.
Actualización por aireCambios de pantallas y textos que llegan a la app instalada sin pasar por la tienda (EAS Update). Solo llegan a las apps con el mismo runtimeVersion.

Cómo viaja la configuración

Antes de rentar: costos y reglas

TemaQué saber
Costo de FirebaseCada negocio tiene su propio proyecto con plan Blaze, de pago por uso. Con poco tráfico suele salir en $0–5 USD al mes, pero lo paga la tarjeta del proyecto. Decide si es la tuya, para incluirlo en la renta, o la del negocio. Ponle siempre una alerta de presupuesto.
Google PlaySi publicas en tu cuenta, tú respondes ante Google por todas las apps. Varias apps casi iguales pueden marcarse como "contenido repetitivo", y si Google sanciona una, el riesgo es para toda la cuenta, incluida PeachGlow. Dale a cada app su propio nombre, ícono, descripción y capturas.
Apple (iOS)La cuenta de Apple Developer cuesta 99 USD al año. Puede ser una tuya para todos o una por negocio.
Datos de los clientesCada negocio es responsable de los datos de sus clientes, incluida la ficha de salud. Necesita su propio aviso de privacidad. Tú, como proveedor, conviene que firmes un contrato con cada negocio como "encargado" del tratamiento.
Mercado PagoSiempre con la cuenta del negocio: los anticipos le llegan directo a él, no a ti.
Solo webUn negocio puede usar solo la web (https://<proyecto>.web.app o su dominio), sin app en la tienda. Te ahorras Play, pero no tiene push nativas ni el botón de Google Wallet.

PeachGlow sigue igual

PeachGlow es el negocio peachglow y es el que se usa cuando no se indica otro. Todo lo de siempre funciona igual:
  • npm run update, npm run build:android, npm run deploy:web y firebase deploy siguen trabajando con PeachGlow.
  • Hacer git push a master sigue desplegando PeachGlow solo, con los secretos del repositorio de siempre.
  • No cambia el paquete com.peachglow.app, ni el proyecto de EAS, ni el runtimeVersion (0cdfd560…), ni Firebase peachglow-9daa8. La versión de la tienda sigue recibiendo actualizaciones.
  • Las cuentas admin no se tocan. Ni la consola ni los comandos cambian roles. PeachGlow conserva su ADMIN_EMAILS en functions/.env.
  • Primer push después de este cambio: el despliegue automático de PeachGlow publica reglas, functions y web, pero no la actualización de la app, porque detecta archivos de configuración nuevos. Córrela una vez a mano con npm run update (es seguro: el runtimeVersion es el mismo). Después todo vuelve a ser automático.
  • Lo que antes estaba en app.json ahora está en tenants/peachglow/tenant.json, y sus imágenes en tenants/peachglow/assets/.

Ejemplo completo: una app como PeachGlow para otra lashista

De cero a la tienda. Caso: Dafne tiene un estudio de pestañas en Mérida y te renta la app. Su app se llamará Lashes by Dafne.

Cada paso dice quién lo hace: Tú (el administrador, desde la consola), Dafne (desde su propia app) o Dev (solo si algo falla). Tiempo total: unas 2 horas de trabajo, más la revisión de Google Play, que tarda días.

Paso 1 · Crea su proyecto de Firebase Tú · 10 min

  1. Entra a console.firebase.google.com con tu cuenta de Google y dale a Crear un proyecto.
  2. Nombre: Lashes by Dafne. Debajo del nombre, edita el ID del proyecto a lashes-dafne-prod. Si está ocupado, usa otro y anótalo.
  3. Google Analytics: desactívalo; no hace falta. Dale a Crear proyecto.
  4. Ya adentro: abajo a la izquierda, Spark → Actualizar → Blaze. Elige tu cuenta de facturación y pon una alerta de presupuesto de, por ejemplo, $5 USD.

No crees apps ni actives servicios: eso lo hace solo el paso 5.

Paso 2 · Crea el negocio en la consola Tú · 5 min

  1. En la consola, arriba: + Nuevo.
  2. Llénalo así:
    • Id interno: lashes-dafne
    • Nombre: Lashes by Dafne
    • Rubro: Pestañas y cejas. Con esto la app dice "clienta", "lashista" y "estudio", trae las categorías Extensiones, Retoques y Lifting, y la ficha de salud de ojos, igual que PeachGlow.
    • Color: #B5838D
    • Paquete: com.lashesdafne.app
    • Project ID: lashes-dafne-prod
    • Soporte: su correo
    • Primera admin: dafne.lashes@gmail.com
    • Módulos: deja todos menos Anuncios (o lo que incluya su plan)
  3. Crear negocio. Te lleva a su ficha. Ya aparece en Negocios con un círculo de su color como ícono de relleno.

Equivalente con comando

npm run tenant -- new lashes-dafne --name "Lashes by Dafne" --industry pestanas --project lashes-dafne-prod --package com.lashesdafne.app --color "#B5838D"

Qué se crea

tenants/lashes-dafne/ con su tenant.json, imágenes de relleno y servicios de ejemplo de pestañas.

Paso 3 · Sube su ícono y logo Tú · 5 min

  1. En el negocio, entra a Imágenes. Para cada imagen, Elegir archivo:
    • Ícono de la app: 1024×1024
    • Ícono Android (frente): el logo sobre fondo transparente, centrado y con margen
    • Ícono Android (fondo): un color liso
    • Logo (símbolo): el de la tarjeta digital
    • Favicon: 48×48
  2. Si una imagen no mide lo recomendado, la consola te avisa antes de subirla.

Paso 4 · Dale a la consola permiso sobre su Firebase Tú · 10 min

  1. Abre Google Cloud → Cuentas de servicio. Arriba, en el selector de proyectos, elige Lashes by Dafne; no PeachGlow.
  2. + Crear cuenta de servicio, con nombre github-deploy. Luego Crear y continuar.
  3. Agrega estos 5 roles, uno por uno, con + Agregar otro rol:
    • Editor
    • Administrador de Cloud Functions
    • Usuario de cuenta de servicio
    • Administrador de Secret Manager
    • Administrador de Firebase
    Después Continuar → Listo.
  4. Abre la cuenta que se creó → pestaña Claves → Agregar clave → Crear clave nueva → JSON → Crear. Se descarga un archivo lashes-dafne-prod-xxxx.json.
  5. En la consola, entra al negocio → Secretos → FIREBASE_SERVICE_ACCOUNT → elige ese archivo → Guardar. Si la llave es de otro proyecto, la consola la rechaza.
  6. Borra el .json de Descargas y vacía la papelera: da acceso a producción.

Paso 5 · Prepara su nube Tú · 1 clic + 10 min de espera

  1. En el negocio, entra a Desplegar → Preparar proyecto en la nube y confirma.
  2. El avance se ve abajo, en Altas; con ver detalle abres GitHub. Al terminar, sin que hagas nada más:
    • Firestore, Storage y el login con correo quedan activados.
    • Quedan creadas su app web y su app Android en Firebase. Su google-services.json real reemplaza al de relleno y su configuración web se guarda en su tenant.json.
    • Su web queda publicada en https://lashes-dafne-prod.web.app.
    • Su proyecto de EAS queda creado, para las actualizaciones de la app.
    • Se cargan los servicios de ejemplo de pestañas y un "Especialista principal".
  3. Si al final de la corrida sale un aviso (ℹ) de Storage o de Correo/contraseña, actívalo a mano en Firebase: Storage → Comenzar, o Authentication → Método de acceso → Correo electrónico/contraseña.
  4. Comprueba: abre https://lashes-dafne-prod.web.app. Debe decir Lashes by Dafne, con su color.
Si falla, abre ver detalle y busca el paso en rojo. Lo más común es que la cuenta de servicio no tenga uno de los 5 roles: agrégalo y vuelve a dar Preparar proyecto en la nube. Se puede repetir sin problema.

Paso 6 · Activa los correos Tú · 15 min

  1. En Firebase (proyecto de Dafne), entra a Compilación → Extensions → Explorar → Trigger Email from Firestore → Instalar.
  2. Configúrala:
    • Colección: mail
    • SMTP: si usas Gmail, en esa cuenta de Google activa la verificación en dos pasos y crea una contraseña de aplicación (myaccount.google.com → Seguridad → Contraseñas de aplicaciones). En SMTP connection URI pon smtps://correo%40gmail.com@smtp.gmail.com:465 (la @ del correo va como %40). En SMTP password pon la contraseña de aplicación.
    • Remitente: Lashes by Dafne <correo@gmail.com>
  3. Al terminar, los recordatorios y avisos por correo ya salen.

Paso 7 · Dafne entra y deja su negocio a su gusto Dafne · 30 min

  1. Dafne abre https://lashes-dafne-prod.web.app → Crear cuenta con dafne.lashes@gmail.com. "Continuar con Google" funciona hasta que configures el login con Google (opcionales). Como es el correo de "primera admin", entra directo a su panel.
  2. En Más → Configuración llena:
    • teléfono, WhatsApp, dirección (con el botón de ubicación) e Instagram;
    • sus políticas;
    • si quiere, su logo y su color; esto no necesita compilar nada.
  3. En Más → Servicios cambia los de ejemplo por los suyos: nombre, duración, precio y anticipo.
  4. En Más → Personal y horarios renombra "Especialista principal" a su nombre, pon su horario y su celular, y agrega a sus lashistas.
  5. Prende lo que quiera usar: recordatorios, lealtad, lista de espera, etc. Son los mismos interruptores que tiene PeachGlow.
Las demás cuentas de su equipo las administra Dafne desde su app. La consola nunca toca cuentas admin.

Paso 8 · Conecta su Mercado Pago Dafne Tú · 15 min

  1. Dafne entra a Mercado Pago → Tus integraciones → Crear aplicación, con tipo Pagos online → Checkout Pro. Te pasa su Access token de producción (APP_USR-…) por un medio seguro, nunca por un chat grupal.
  2. Tú En la consola, entra a Secretos → MP_ACCESS_TOKEN → pégalo → Guardar.
  3. Dafne En Mercado Pago, Webhooks → Modo productivo: URL https://us-central1-lashes-dafne-prod.cloudfunctions.net/mercadoPagoWebhook (la consola la muestra en Secretos), evento Pagos, y guarda. Copia la clave secreta.
  4. Tú Entra a Secretos → MP_WEBHOOK_SECRET → pégala → Guardar. Cada secreto se copia a Firebase y las functions se vuelven a desplegar solas; el avance se ve en Desplegar.
  5. Dafne Prueba con una cita real de poco monto y luego reembolsa.

Paso 9 · Aviso de privacidad y datos legales Tú · 10 min

  1. Publica el aviso de privacidad de Dafne. Puedes adaptar el de PeachGlow con sus datos; ella es la responsable de los datos de sus clientas.
  2. En la consola, ve a Configuración → Legal y contacto: URL del aviso, URL para eliminar la cuenta (la misma con #eliminar-cuenta) y correo de soporte. Luego Guardar.

Paso 10 · Su llave de firma para Play Tú Dev · 10 min

  1. Crea su keystore. Es una sola vez y es distinta a la de PeachGlow: 
    keytool -genkeypair -v -keystore lashes-dafne-upload.jks -alias upload -keyalg RSA -keysize 2048 -validity 10000
    Anota las contraseñas en tu gestor de contraseñas.
  2. En la consola, entra a Secretos y guarda:
    • ANDROID_KEYSTORE_BASE64: elige el .jks
    • ANDROID_KEYSTORE_PASSWORD
    • ANDROID_KEY_ALIAS: upload
    • ANDROID_KEY_PASSWORD
  3. Respalda el .jks fuera del repo (USB o gestor de contraseñas).

Paso 11 · Compila su app Tú · 1 clic + 20 min

  1. Entra a Compilar → Compilar .aab (Android).
  2. Al terminar, aparece en .aab listos. Abre el enlace → sección Artifacts → descarga aab-lashes-dafne (un .zip con el .aab adentro).

Paso 12 · Publícala en Google Play Tú · 1 h + días de revisión

  1. En Play Console → Crear app: nombre Lashes by Dafne, idioma Español (Latinoamérica), App, Gratis.
  2. Llena la ficha: descripción, ícono 512 (está en Imágenes → "Ícono para Play Store"), gráfico de funciones y capturas de su web o de su app.
  3. Llena Contenido de la app igual que PeachGlow: anuncios (No, si quitaste el módulo), seguridad de los datos, público objetivo y el link de eliminación de cuenta.
  4. Sube el .aab a Prueba cerrada con al menos 12 testers durante 14 días. Después solicita el acceso a producción, como hiciste con PeachGlow.
  5. Cuando Google lo apruebe: Producción → Crear versión con ese mismo .aab.
Si publicas varias apps casi iguales en tu cuenta, Google puede marcarlas como contenido repetitivo. Haz que cada una tenga su propio nombre, ícono, descripción y capturas.

Paso 13 · Verifica que todo funcione Tú Dafne

  • ☐ La web y la app dicen "Lashes by Dafne", con su color y su ícono; nada dice PeachGlow.
  • ☐ Una clienta de prueba se registra, agenda, paga el anticipo y le llega el correo de confirmación.
  • ☐ Dafne ve la cita en su agenda y le llega el aviso.
  • ☐ El recordatorio llega un día antes, por correo y push.
  • ☐ En la consola → Negocios, "Último despliegue" sale en ✔.

👩‍💼 Entrar a la consola

La consola es una página web. No guarda datos propios: entras con un token de GitHub, que es como una llave de acceso al repo.

  1. En GitHub, entra a tu foto → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
  2. Ponle de nombre consola y una caducidad (por ejemplo, 90 días). En Repository access elige Only select repositories y marca el repo de la app.
  3. En Permissions → Repository permissions da Read and write a Contents, Actions, Secrets, Environments y Workflows. Metadata queda en solo lectura.
  4. Copia el token (empieza con github_pat_). Abre la consola en https://<tu-usuario>.github.io/peachglow-consola/ (ver Configuración única de GitHub) y pégalo. Se borra al cerrar la pestaña.
  5. Cuando el token caduque, la consola te regresa a la pantalla de entrada: crea otro igual y listo.
El token da acceso a producción: no lo compartas ni lo pegues en chats. Si se filtra, bórralo en esa misma página de GitHub.

Dar de alta un negocio

Necesitas: nombre del negocio, su rubro, su color, una cuenta de Google para su Firebase y, si cobrará en línea, su cuenta de Mercado Pago.

  1. Crea su proyecto de Firebase. En console.firebase.google.com, entra a Agregar proyecto y ponle un id como nails-ana-prod. Después ve a Actualizar → plan Blaze y pon una alerta de presupuesto.
  2. Crea el negocio.

    Consola

    + Nuevo negocio. Llena los datos y los módulos del plan, y dale a Crear negocio.

    Comando

    npm run tenant -- new nails-ana --name "Nails by Ana" --industry unas
  3. Crea su cuenta de servicio. En Google Cloud → Cuentas de servicio, con el proyecto del negocio elegido: Crear cuenta de servicio → nombre github-deploy. Dale los roles Editor, Administrador de Cloud Functions, Usuario de cuenta de servicio, Administrador de Secret Manager y Administrador de Firebase. Luego entra a Claves → Agregar clave → JSON.
  4. Guárdala.

    Consola

    El negocio → Secretos → FIREBASE_SERVICE_ACCOUNT → elige el archivo .json → Guardar.

    Comando

    npm run tenant -- secrets set nails-ana FIREBASE_SERVICE_ACCOUNT --file ruta.json
    Después borra el .json de tu computadora.
  5. Prepara la nube. En la consola, entra al negocio → Desplegar → Preparar proyecto en la nube. Esto:
    • activa Firebase, Firestore y el login con correo;
    • crea las apps web y Android, y baja su google-services.json;
    • crea los secretos de relleno y el proyecto de EAS;
    • despliega todo y carga los servicios de ejemplo.
    Tarda unos 10 minutos.
  6. Correos. En Firebase, entra a Extensions e instala Trigger Email from Firestore con la colección mail y el SMTP del negocio. Puede ser Gmail con contraseña de aplicación, o SendGrid.
  7. Su aviso de privacidad. Cada negocio es responsable de los datos de sus clientes. Publica su aviso y pon la URL en Configuración → Legal y contacto.
  8. Sus imágenes. Entra a Imágenes y sube el ícono y el logo del negocio, para reemplazar el círculo de relleno.
  9. La primera admin. La persona del correo que pusiste en "primera admin" crea su cuenta en la web del negocio y queda como admin. Después, las demás cuentas las administra ella desde su app.
  10. Tienda. Compila el primer .aab (ver Compilar y subir a Play) y crea su ficha en Play Console.

Mercado Pago de un negocio

  1. El negocio crea su app en Mercado Pago → Tus integraciones: tipo Pagos online → Checkout Pro.
  2. Copia el Access token de producción (APP_USR-…).
  3. En Webhooks → Modo productivo registra la URL que muestra la consola (Secretos → Mercado Pago), con el evento Pagos. Copia la clave secreta.
  4. Guárdalos:

    Consola

    Secretos → MP_ACCESS_TOKEN y MP_WEBHOOK_SECRET → Guardar. Se copian a Firebase y se redespliega solo.

    Comando

    npm run tenant -- secrets mp <id> (te pide los dos valores sin mostrarlos)
  5. Haz un pago real pequeño y reembólsalo para probar.

Publicar cambios

Todo cambio que guardes se despliega solo. Pasa por las pruebas (CI) y luego se publica en cada negocio afectado: las reglas, las functions, la web y la actualización de la app.

  • Si cambias el código (src/), se actualizan todos los negocios activos.
  • Si cambias la configuración de un negocio, solo se actualiza ese negocio.
  • Si algo exige .aab nuevo, la actualización por aire no se publica y queda un aviso en la pestaña Desplegar.

Consola

El negocio → Desplegar: botones para desplegar todo o una parte, e historial con los resultados.

Comando

npm run tenant -- deploy <id> all
npm run tenant -- update <id> --message "…"

Compilar y subir a Play

  1. Sube la versión: Compilar → Subir versionCode. Si cambiaste algo 🔶 o librerías nativas, usa Nueva versión nativa.
    Comando: npm run tenant -- bump <id> (o con --native)
  2. Compilar → Compilar .aab. Tarda unos 20 minutos. Necesita el keystore del negocio en Secretos (ANDROID_KEYSTORE_BASE64 y sus contraseñas).
    En la PC: npm run tenant -- build <id> android, con las propiedades <PREFIJO>_UPLOAD_* en ~/.gradle/gradle.properties.
  3. En Compilar, elige en "Al terminar de compilar" a dónde subirlo (Producción, Prueba cerrada… o solo compilar) y dale Compilar .aab. Si elegiste una pista, queda como borrador en Play Console: entra y dale Enviar a revisión. Si elegiste solo compilar, descárgalo en .aab listos y súbelo a mano (Play Console → la app → Producción → Crear versión). Requiere la llave de Play.

Publicar en la tienda con cada versión nueva, sin tocar nada

En la consola → el negocio → Configuración → Tienda (publicación automática) elige a qué pista subir (Producción, Prueba cerrada…) y qué hacer: borrador, enviar a revisión al 20% o a todos. Desde entonces:

  • Cuando un push sube el versionCode del negocio, GitHub despliega como siempre y además compila el .aab y lo sube a Google Play, usando el mensaje del commit como notas de la versión. Quién sube el versionCode: la consola al guardar un cambio 🔶 o al subir una imagen de la app, o tú con bump.
  • Los pushes normales (pantallas, textos, arreglos) no pasan por la tienda: llegan por actualización automática.
  • Con "No", compilas y subes cuando quieras desde la pestaña Compilar.

Desactivar o eliminar un negocio

  • Desactivar (Eliminar → Desactivar): deja de desplegarse, pero se conserva todo. Su app sigue funcionando. Es reversible.
  • Eliminar (escribe el id para confirmar): borra su carpeta del repo y, si lo marcas, sus secretos de GitHub.

Eliminar no borra su proyecto de Firebase, ni EAS, ni la app en Play. Hazlo a mano solo cuando estés seguro: los datos de sus clientes se pierden. PeachGlow no se puede eliminar.

Textos con "clienta" en pantallas nuevas

No escribas "clientas" fijo: usa w de @/lib/industry. Por ejemplo, `${w.Ninguna} ${w.client} cumple años` sale "Ninguna clienta…" en PeachGlow y "Ningún cliente…" en una barbería. El CI falla si la web de la plantilla contiene "PeachGlow".

Qué revisa el CI

  • Typecheck, lint y pruebas de la app, de las functions y de las reglas (como siempre).
  • npm run tenant -- validate: todos los negocios son válidos y no repiten paquete, proyecto ni site.
  • PeachGlow sin cambios: mismo nombre, paquete, projectId de EAS y runtimeVersion.
  • Sin fugas de marca: la web y la configuración de la plantilla no contienen "PeachGlow".
  • Proyecto nativo: el prebuild de la plantilla genera su paquete y su firma.

Si el CI pasa en master, el workflow Deploy calcula qué cambió (tenant plan) y despliega cada negocio con los secretos de su Environment. Antes de desplegar revisa que la cuenta de servicio sea del proyecto correcto.

Errores comunes

"La cuenta de servicio de X es del proyecto Y"

Guardaste en el Environment del negocio la cuenta de otro proyecto. Vuelve a guardar en Secretos el .json correcto. Esta revisión evita desplegar un negocio en el Firebase de otro.

"La app de X usa el proyecto P, pero el .env es de Q"

Falta la configuración web de Firebase en su tenant.json. Corre "Preparar proyecto en la nube" o copia los valores de Firebase → Configuración → Tus apps → Web con set <id> firebase.apiKey …. En la PC usa EXPO_NO_DOTENV=1.

Deploy falla con 403 / Permission denied

A la cuenta de servicio le falta un rol. Revisa en IAM los roles de la sección Alta y vuelve a correr el despliegue.

"Accessing secret failed … Permission denied on secret"

Una función usa un secreto que no existe o se borró. Créalo de nuevo (con "-" si no se usa), o borra la función y vuelve a desplegar. Las functions declaran todos sus secretos, así que todos deben existir.

google-services.json "de relleno" o con otro paquete

Descarga el real: Firebase → Configuración del proyecto → Tus apps → Android (el paquete del negocio) → google-services.json, y súbelo a tenants/<id>/. "Preparar proyecto en la nube" lo hace solo.

El .aab sale firmado con la llave de prueba / Play lo rechaza

Faltan las propiedades <PREFIJO>_UPLOAD_* (PC) o los secretos ANDROID_KEYSTORE_* (consola). El comando build se detiene antes de compilar si faltan.

En Windows: "ninja: error: mkdir" al compilar

Son las rutas largas. build pone cmake.dir (CMake 3.31.6) en android/local.properties. Si sigue fallando, borra las carpetas .cxx y vuelve a compilar.

"dist/ es la web de X, no de Y" al hacer firebase deploy

Es un candado: en dist/ quedó la web de otro negocio (la última que se exportó). Vuelve a exportar la correcta con npm run tenant -- build-web <id>, o usa npm run tenant -- deploy <id> web, que hace las dos cosas.

"android/ es de X, no de Y" con npm run build:android

Es otro candado: la carpeta android/ se generó para otro negocio. Usa npm run tenant -- build <id> android, que la regenera para el negocio correcto antes de compilar.

Guardé en la consola y dice "Alguien más cambió este negocio"

Mientras editabas, otra persona o un workflow (por ejemplo "Preparar proyecto en la nube") guardó cambios en ese negocio. Recarga la página y vuelve a hacer tu cambio. Así no se borra lo que guardó el otro.

Un negocio nuevo no aparece en los despliegues

Hasta que no se corre "Preparar proyecto en la nube" (que llena su firebase.apiKey), el despliegue automático lo salta. Si su cuenta de servicio no es de su proyecto, se salta con un aviso, sin fallar.

Cambié de negocio y la app sigue mostrando el anterior

Es la caché de Metro. Arranca con --clear.

La actualización no le llega a la app instalada

El runtimeVersion de tenant.json debe ser el mismo con el que se compiló el .aab de la tienda. Revisa la pestaña Compilar y el aviso del último Deploy.
